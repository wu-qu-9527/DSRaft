# Raft 待办清单

当前已完成固定成员集群的选举、心跳、任期/投票持久恢复及本地日志存储；已支持 AppendEntries 日志复制，尚未实现业务命令的多数提交。
下列任务按依赖顺序推进，完成任务后勾选对应条目。

## 已有能力

- [x] Follower、Candidate、Leader 角色及轻量状态分发。
- [x] 随机选举超时、任期递增、自投票和多数票判断。
- [x] 重复选票去重、旧任期选票过滤、更高任期退回 Follower。
- [x] 授票前检查候选者最后日志的任期与索引。
- [x] 周期性心跳、有效 Leader 联系后重置选举计时器。
- [x] 节点间 RPC 类型与响应 ID 检查、超时取消和连接重建。
- [x] 选举、心跳、协议编解码和 RPC 超时相关单元测试。
- [x] 进程级验证：三节点选举、仅两节点在线时选举、Leader 停止后重新选举。
- [x] 当前终端及 SSH 下通过 tmux 启动演示集群。

以上不代表已经实现完整 Raft。普通客户端请求仍直接返回示例响应，没有经过日志复制与提交。

## 第一阶段：持久化任期和投票记录（优先级 P0）

目标：节点重启后仍遵守任期不回退、同一任期最多支持一个候选者的规则。

- [x] 定义节点独立的数据目录和稳定存储接口。
- [x] 持久化当前任期 `currentTerm` 和投票记录 `votedFor`。
- [x] 启动时恢复持久状态，以 Follower 身份参与集群。
- [x] 发起选举时，在发送 RequestVote 前持久化新任期和自投票记录。
- [x] 观察到更高任期时，持久化任期更新及旧投票的清除；授票前持久化新的投票记录。
- [x] 明确原子更新、落盘时机和损坏检测，避免恢复出不一致的任期与投票组合。
- [x] 存储失败时停止相关协议操作，禁止返回授票成功等依赖持久化的成功结果。

验收：投票后强制终止并重启，不会在同一任期投给另一候选者；更高任期更新后重启不会回退。模拟写盘失败和不完整记录时，不得静默按全新节点启动。

## 第二阶段：日志存储与完整 AppendEntries（优先级 P0）

目标：Leader 能将真实命令复制到 Follower，并修复日志分歧。

- [x] 定义日志条目，包含索引、任期和状态机命令（`src/server/log_entry.hpp`）。
- [x] 实现日志读取、追加、后缀截断、持久化与启动恢复。
- [x] 从真实日志推导最后日志索引和任期，供 RequestVote 使用。
- [x] 将空心跳扩展为携带日志条目列表的 AppendEntries；空列表继续承担心跳职责。
- [x] Follower 校验前置日志的索引与任期，拒绝不匹配请求。
- [x] Follower 删除冲突的未提交日志后缀并追加新条目，保护已提交日志不被覆盖。
- [x] Follower 在确认复制成功前完成必要的日志持久化。
- [x] Leader 为每个 Follower 维护 `nextIndex`、`matchIndex`，根据响应调整复制位置。
- [x] 支持批量复制、失败重试及落后节点追赶，过滤旧任期和过期请求的响应。

验收：Follower 离线一段时间后可追上；不同未提交日志后缀能够收敛；重复请求不产生重复条目；节点重启后恢复已确认持久化的日志。

## 第三阶段：多数提交与状态机执行（优先级 P0）

目标：日志被安全提交并执行后，才形成业务结果。

- [ ] Leader 根据多数成员的复制进度推进 `commitIndex`，计算成员数时包含自己。
- [ ] 仅通过统计多数副本直接提交当前任期条目，使此前日志随之间接提交。
- [x] 通过 AppendEntries 将 Leader 的提交位置传给 Follower，并限制在已确认匹配的范围内。
- [ ] 引入 `lastApplied`，按索引顺序应用已提交日志，保持 `lastApplied <= commitIndex`。
- [ ] 实现一个确定性的示例状态机，例如键值存储，替换直接返回 Hello 的业务路径。
- [ ] 明确重启后的提交位置恢复、日志重放和状态机恢复策略，防止执行未提交日志或重复产生外部副作用。
- [ ] Leader 当选后追加当前任期的 no-op 条目，以推动此前日志的提交。

验收：三个投票成员需要至少两个确认才可提交；只剩一个节点时不能成功提交新命令；换 Leader 后已提交命令保持不变；各节点按相同顺序执行已提交命令。

## 第四阶段：客户端写入语义（优先级 P1）

依赖：日志复制、提交与状态机执行已经打通。

- [ ] 仅 Leader 接受共识写请求；Follower 返回已知 Leader 信息，未知时返回明确错误。
- [ ] 写请求在日志提交且应用后返回结果，不能只在本地追加成功或网络发送成功后回复。
- [ ] 失去多数、请求超时或领导权变化时，返回适当错误，不把未确认提交的请求当作成功。
- [ ] 为客户端定义重试与 Leader 发现策略；明确超时可能意味着结果未知，不等于命令未执行。
- [ ] 引入客户端身份和请求序号，在状态机中保存去重信息及结果，支持安全重试。
- [ ] 调整客户端交互协议及服务端响应方式，使等待提交期间仍能处理选举、心跳和其他节点的 RPC。

验收：孤立 Leader 不能返回新的成功写入；切换 Leader 后客户端可重试；同一请求重复提交不会重复执行。

## 工程改进（优先级 P1）

- [x] 将全局 `vote_state` 迁入 `server` 实例，确保同进程多个节点不会共享任期和投票状态。
- [ ] 统一角色迁移入口，明确任期、投票、Leader 信息、计时器及待处理 RPC 的更新规则。
- [ ] 区分网络暂时错误与存储错误，避免普通非阻塞收发失败直接导致整个服务退出。
- [ ] 为 REP socket 定义失败后的恢复策略，遵守收发状态机约束。
- [ ] 允许配置选举超时、心跳间隔、RPC 超时和数据目录，并校验参数范围。
- [ ] 将进程级故障验证整理为可重复运行的自动化测试，隔离端口、数据目录和进程并确保清理。

## 核心故障测试与安全性验收

以下属于对应阶段的完成条件，应随实现补充，不集中留到最后。

- [x] 持久化测试：授票后重启、更新任期后重启、写盘失败及不完整记录恢复。
- [ ] 复制测试：重复、延迟、丢失消息；日志分歧修复；落后节点追赶。
- [ ] 提交测试：旧任期条目不能仅凭多数直接提交，已提交日志不能被新 Leader 覆盖。
- [ ] 三节点故障测试：分别停止 Leader 和 Follower；两个存活节点互通时仍可提交。
- [ ] 多数丢失测试：只剩一个节点，无论其是否自认为 Leader，都不得成功提交新命令。
- [ ] 分区恢复测试：网络分成 2 + 1，再恢复连接；旧 Leader 退位并修复日志。
- [ ] 客户端测试：提交前后丢失响应、超时重试和 Leader 切换，不重复执行同一命令。
- [ ] 持续检查不变量：同任期最多一个当选 Leader、同日志位置不应用不同命令、各节点任期不回退。

## 后续增强（优先级 P2）

以下功能不应替代前面的多数提交及持久化规则。

- [ ] CheckQuorum：Leader 长时间无法联系多数成员时主动退位；不能替代提交判断。
- [ ] PreVote：降低隔离节点恢复后发起高任期选举对集群的扰动。
- [ ] 线性一致读：实现读屏障或 ReadIndex 等机制，确认领导权并等待状态机应用到所需位置。
- [ ] 快照与日志压缩：保存状态机快照、截断旧日志并支持 InstallSnapshot 和重启恢复。
- [ ] 动态成员变更：使用安全的配置转换机制，避免新旧成员集合分别形成互不相交的多数。
- [ ] 主动领导权转移：为维护、升级或负载调整提供受控的 Leader 切换。
- [ ] 运行观测：统计角色、任期、提交和应用进度、选举次数、RPC 延迟及超时。

推荐推进顺序：持久化任期与投票 → 日志存储与复制 → 多数提交与状态机 → 客户端写入闭环 → 安全读、快照及成员变更。
